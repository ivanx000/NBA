anyone at a keyboard.

## The jobs (GitHub Actions)

| Time (ET) | Job | What it does |
| --- | --- | --- |
| ~06:07 | `schedule-sync` | Updates the season's games (dates, times, final scores) from the cdn schedule |
| Mon ~07:17 | `retrain` | Refits the game and player models on every completed game, scores each refit on a walk-forward over the last 4 complete weeks, and promotes it only if it's no worse than what was published for those games (log loss within 0.005; player MAE within 1%). Otherwise it keeps the champion and opens an issue |
| 09:05, retried 12:05 | `daily` | Pulls the staged history and champion models, adds box scores for newly finished games, fetches the official injury report as of 9 AM, builds features, predicts today and projects its players, publishes, then fills in yesterday's real player lines. Stops once today is published. A missing injury report never stops it |
| 17:50 | `daily --refresh` | Fetches the 5:45 PM injury report, re-predicts today's games and players, and re-publishes the games that haven't started. Once a day |
| 10:40 | `freshness-check` | Fails (and emails) if any of today's games lacks a live prediction |
| Hourly ~18:17–02:17 | `results-sync` | Live status and final scores, which grade the predictions |

GitHub runs scheduled workflows as best effort, and in this repo they started 5 to 11 hours late,
so the site's host starts the prediction jobs instead: Vercel Schedules fire at the ET times above
(within 15 minutes) and call a small protected route that asks GitHub to run the workflow now.
Each workflow keeps its own GitHub schedule as a backstop, and every job does nothing if its work
is already done, so a second run is harmless. The other jobs still run on GitHub's schedule, whose
UTC times drift by an hour with daylight saving.
The retrain shares the daily job's queue, so the two never touch the stored state at once.

## State between runs

The cloud job has no disk, so the staged history (about 5 MB of parquet, injury reports included) and the two champion models
(game and player) live in a `pipeline_state` table. Each run pulls them (checking a SHA-256), adds the new games, and pushes
the history back.

## Keeping it honest

- `publish` refuses to write a prediction for a game that has started, and the database upsert also
  requires the tip-off time to be in the future, so a slow run can't sneak in a "prediction" after
  the fact.
- Every prediction stores its model version and `features_hash`.
- The [performance page](/performance) is the monitor: every finished game is graded against Elo and
  the home team.

## Tests and CI

Every push runs `pytest` (including the [leakage test](/docs/leakage)) and `ruff` for the pipeline,
and lint, type checks, Vitest and a production build for the website. The same checks run locally
through a `pipeline.yaml` file.
